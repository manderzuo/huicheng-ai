# 小红书截流（A 采集 / B 回复）实测记录

设备：手机3 `192.168.31.214:5555`，Galaxy S10 / Android 12，小红书 `v.9.4.0.8a83615`。
时间：2026-11-01 01:02 起。

> 标注规则：**真机跑通过的才写「已实测」**，只写代码没跑的一律「未验证」。

## 一、核心结论：为什么必须用小红书号

实测搜「隔壁小马」→ 用户页返回 **4 个以上同名账号**（粉丝 16.8万 / 996 / 272 / 262），
仅靠昵称**无法区分**。

实测搜 `95288842605` → 只返回 1 个，并显示「无更多用户」。

**结论：昵称只用于人工核对，唯一键必须是小红书号。**

## 二、小红书号的真实格式（原方案写错过）

实测同一屏里就有两种形态：

```
小红书号：992771452      ← 纯数字
小红书号：iiiu0417o      ← 含字母
小红书号：5066803166
```

最初的解析正则写的是 `^小红书号[：:]\s*(\d+)$`，**会直接漏掉含字母的号**。
已改为 `[A-Za-z0-9_.\-]{3,30}`。

另外有用户**根本不显示小红书号**（该位置显示行业标签，如「家电电器」），
所以取号必须允许缺失，并在结果里明确标注「无法用于 B 端定位」。

## 三、用户列表的布局坑（原方案写错过）

一张用户卡的实际纵向布局：

```
昵称                    y≈395
粉丝 1557               y≈457     ← 离「小红书号」更近
小红书号：992771452      y≈508
```

原逻辑按「同一行、号左侧最近的文本」取昵称，**必然取不到**（号在昵称下方约 113px）。
已改为：昵称在号**上方 30–180px**、左对齐、并排除 `粉丝/关注/发过相关笔记` 等行。

修复后用真实一屏验证，5 个号昵称全部配对正确，含字母的 `iiiu0417o` 也正确取出。

## 四、笔记详情页的读取方式（原方案写错过）

以为正文在带 label 的容器里（发布自己的笔记时确实有 `noteContentLayout` label），
但**别人的图集笔记不是**：

- 标题与正文是**普通 TextView，没有 label**；
- **首屏往往不渲染**（首屏只有 100 个元素、正文空白），必须**向上滑一次**才出现；
- 作者昵称在顶部 y≈175，紧邻「关注」；
- 「共 N 条评论」是正文区下边界。

实测修正后读到：

```
标题：📍郑州！花小钱可以坐一下午的地方！（3/100）
作者：隔壁小马🐎
```

> 顺带印证：同一篇笔记的标题编号从 `(3/100)` 变成过 `(14/100)`，
> **作者会改标题，标题不能当主键**。

## 五、评论区解析（锚点法 + 昵称尽力而为）

评论区没有汇总 label，用「时间 地区 回复」做锚点：

- **正文** = 锚点上方 160px 内**最近**的 TextView → 实测 4/4 正确；
- **昵称** = 正文上方 25–90px，但该区间会混进
  「展开 N 条回复」、「爱评论的人运气都不差」、以及**上一条评论的正文**。

修正后实测结果（同一条 53 评论的笔记）：

| # | 昵称 | 正文 | 时间 地区 |
|---|---|---|---|
| 1 | 伤心故事像苦瓜 | 好漂亮啊这里 | 08-14 河北 |
| 2 | 隔壁小马🐎 | 坐这个窗边的沙发上写周报真的美滋滋[捂脸R] | 08-14 河南 |
| 3 | 王奕之 | 这个地方可以聊天吗 | 08-23 河南 |
| 4 | 王奕之 | 肆无忌惮的，可以稍微不那么小声的 | 08-23 河南 |

昵称是**尽力而为**：确认不了就留空，绝不猜。定位只用号。

## 六、A → B 闭环已跑通（单机单账号）

因为只有一台手机，A 采集完不能马上切 B 回复；本方案靠「可重定位指纹」解耦。

实测链路：

```
搜索「郑州咖啡」→ 进笔记（53 条评论）
  → 读评论，命中「王奕之 / 这个地方可以聊天吗」
  → 点该评论左侧头像（84×84，y 差 113）
  → 进入他人主页（出现「私信」按钮）
  → 读到 小红书号：1140648862
  → 返回搜索页，直接搜 1140648862
  → 用户 Tab 唯一命中，昵称「王奕之」一致
```

**A 端采到的号，B 端能重新找到同一个人。** 这是本方案成立的关键，已验证。

### 那 3 个不是「号的锅」

对 3 个失败样本原样复测，**全部唯一命中**：

```
6577921571 → 健身华哥，屏上 1 个用户，提示「无更多用户」
kafei0     → 咖啡（粉丝 45.6万），屏上 6 个相似号，但只有它的号是 kafei0
534649681  → 在陶咖啡，屏上 1 个用户，提示「无更多用户」
```

根因是**时序**：切到「用户」Tab 后固定 `sleep 2.4` 就读，拿到的是切换前的旧内容。
→ 已把固定等待改成**稳定性等待**（连续两次读到的号集合一致才承认加载完），
模块 `relocate_by_id` 与压测脚本都已同步修改。

### 结论

- **多命中 0 次**：没有任何一次出现「同一个号搜出多个人」，唯一性成立。
- 偶发失败全部由等待策略导致，不是号的唯一性问题。
- 含字母的号（`kafei0`、`han_s_life`、`BV_ROLEX` 等）同样能唯一命中。
- 101 次搜索未触发安全验证，但风险仍在，脚本保留检测与立即中止。

## 八点五、这套测试怎么复现（方法沉淀）

1. **采样要散**：关键词必须跨互不相干的领域，不能集中在一个圈层；
   本次用了 30 个领域（15 个通用 + 15 个垂直），避免样本偏。
2. **判定口径要硬**：
   - 唯一命中 = 结果里该号恰好出现 1 条
   - 多命中 = 该号出现 ≥2 条（说明号不唯一，方案作废）
   - 零命中 = 搜不到
   - 风控 = 出现安全验证，立即中止并保留已完成结果
3. **必须增量落盘**：每完成 1 条就写一次 JSON，进程被杀也不丢进度。
4. **必须稳定性等待**：切 Tab 后连续两次读到的号集合一致才承认加载完成，
   固定 `sleep` 会读到旧内容，制造出假的「零命中」。
5. **失败样本必须复测**：第一轮 3 个失败复测后全部命中，才发现是等待时机问题，
   而不是号的唯一性问题。不复测就会把工程缺陷误判成方案缺陷。

## 九、已知限制

1. 评论区首屏只渲染 4 条左右，滚动加载的评论解析逻辑还没实测。
2. 「展开 N 条回复」里的评论需要点开才能读，当前会把它当作标记跳过。
3. 搜索结果卡片没有 label，靠封面尺寸（300–620 宽 / 300–900 高）识别，
   换机型或换版本可能需要重新校准。
4. **企业号/店铺号常常不显示小红书号**（第三行是「官方账号」「宠物生活」等行业标签），
   实测「宠物」这个关键词采到的号是 **0** 个。这类账号无法用号定位，必须标为不可用。
5. 频繁搜号有风控风险，批量脚本已加「安全验证/操作过于频繁」检测并会立即中止。

### 发送键的真实判定方式（修正了之前的认知）

之前记录的是「私信发送键没有 disabled」，实测比这更明确：

| 状态 | 发送键 |
|---|---|
| 输入框为空 | **按钮根本不存在**（text=None, label=None） |
| 输入框有字 | `发送` 出现（TextView，y≈1619） |
| 清空后 | **按钮再次消失** |

**结论：私信发送键是「有内容才动态出现」，不是靠 disabled 控制。**
所以判定条件应该是「发送键是否存在」，比「输入框是否非空」更可靠——
后者只是间接推断，前者直接读按钮本身。

### ⚠️ 决定性限制：首次私信最多只能发 1 条

1. **每个潜客只有一次机会**，私信内容必须一次到位，不能试探、不能补发；
2. 文案模板必须质量过硬，发错就再无补救；
3. 这也解释了为什么陌生人营销私信容易被平台限制。

## 三十八、「作者」相关的两处误判（2026-11-02 02:15）

统计发现部分轮次「作者过滤」高达 11–12 条，对一篇 28 条评论的笔记来说太夸张了。
排查出两个连带问题，都出在把「作者」当成前缀匹配。

### BUG 10：正文以「作者」开头会被整段丢掉

评论区正文候选筛选里用了 `startswith(COMMENT_MARK_PREFIXES)`，
而前缀表里含「作者」。于是像「作者写得真好我认同」这种评论**整段被跳过**，
程序转而把上面的昵称当成了正文。

→ 已修：前缀表移除「作者」，改为精确匹配（`text == '作者'`），
并抽出 `_is_comment_mark()` 统一判定。

### BUG 11：作者标签判定过宽，会误杀真实线索

`is_author` 判断用 `text.startswith('作者')`，任何以「作者」开头的文本都会
被认成作者标签，把评论区里正好这么开头的用户当作「作者本人」跳过。

→ 已修：标签长度限制 ≤ 4 字，纵向范围收紧到 -60 ~ 150。

### 验证（离线）

```
真作者标签        → 昵称=作者小号  正文=自问自答        is_author=True   ✓
正文以作者开头    → 昵称=路人甲    正文=作者写得真好…   is_author=False  ✓
```

修复前第二种情况正文会读成「路人甲」（错），现在正确读到完整评论。

### 附带增强

作者过滤计数拆成两路：`author_badge`（标签识别）与 `author_nick`（昵称等于作者）。
日志输出形如 `作者过滤徽章1/昵称1`，便于判断哪条路径在起作用、是否有误杀。

## 四十、重大 BUG：评论时间格式只认绝对日期（2026-11-02 02:50）

核实「作者徽章 9 条」时顺手打开一篇笔记，发现页面上明明有评论，
`read_comments()` 却返回 **0 条**。

### 真相

评论锚点的实际文本长这样：

```
5天前 江苏 回复
昨天 20:09 湖北 回复
刚刚 回复
3分钟前 广东 回复
```

而原来的正则只认 **`MM-DD`** 这一种：

```python
TIME_RE = re.compile(r'^(\d{2}-\d{2})\s*(\S*)?\s*回复$')
```

于是所有**相对时间**的评论都被当成「不是评论锚点」直接忽略。

### 影响有多大

这是静默失败：不报错、不提示，只是**评论莫名变少**。
很多轮次「0 命中」很可能就是因为它——不是没意向，是压根没读到。

### 修复

```python
TIME_RE = re.compile(
    r'^(?P<time>刚刚|\d+\s*分钟前|\d+\s*小时前|\d+\s*天前'
    r'|昨天(?:\s*\d{1,2}:\d{2})?|前天(?:\s*\d{1,2}:\d{2})?'
    r'|\d{4}-\d{2}-\d{2}|\d{2}-\d{2})'
    r'\s*(?P<region>[^\s]*)?\s*回复$')
```

覆盖：刚刚 / N 分钟前 / N 小时前 / N 天前 / 昨天 / 前天 / 绝对日期。

### 同一页面前后对比

| | 修复前 | 修复后 |
|---|---|---|
| 解析到的评论 | **0 条** | **4 条** |

修复后四条评论的作者判定也完全正确：

```

fufu      是的宝[萌萌哒R]       作者 ✓
```

## 四十二、评论覆盖率只有 10%：取号会把评论列表顶回顶部（2026-11-02 03:20）

修完时间格式后，我加了一个「覆盖率」指标：**页面声明的评论总数 vs 我们实际读到的条数**。

首测结果：

```
读评论 40 / 页面声明 369 = 覆盖率 10.8%
```

也就是说页面有 369 条评论，我们只读到 40 条。

### 定位过程

1. 先怀疑滑动失效 → 写了 `diag_scroll.py` 实测：
   每屏能读出 1 → 4 → 6 → 5 → 6 条，**滑动本身是好的**；
2. 再对照代码逻辑发现真正原因：
   **点头像进对方主页取号，返回后评论区会跳回顶部**。
   下一屏读到的全是已见过的评论，被 `fresh_rows == 0` 判定成「到底了」，
   两屏后就提前收工。

### 修复

记录当前已经下翻的屏数 `depth`，每次取号返回后**重新滑回原来的深度**，
再继续读下面的评论。

同时把「到底了」的判定改成：连续 2 屏**没有任何新评论**才算到底，
而不是「没有新命中」就停。

### 效果

| 版本 | 覆盖率 | 单轮读到的评论 |
|---|---|---|
| 修复时间格式前 | — | 约 25 条 |
| 修复时间格式后 | 11.9% | 45 条 |
| **加深度恢复后（v21）** | **39.4%** | **89 条** |

单轮评论量从 45 提升到 89，池子从 399 涨到 427。

## 五十八、租约回收测试挖出 BUG 13：attempts 会无限累加（2026-11-02 06:45）

测试「认领 → 超时 → 回收 → 再认领」时发现不对劲：
重新认领到的线索 `attempts=10`，可它从没失败过。

### 根因

`claim()` 每次都 `attempts+1`，而 `release()`（主动放回）**不清零**。

后果很严重：

1. 正常的「认领→放回」循环会把 attempts 累加到 3 以上；
2. 一旦某次真超时，`reclaim_expired` 看到 `attempts>=MAX_ATTEMPTS(3)`，
   直接判定「多次认领都没有回报结果，已放弃」，把线索扔进 skipped。

**实测代价**：我的并发测试（675 次认领）之后，4 条正常线索被误判放弃：

```

盐粒粒🍀      attempts=11
陈皮话梅糖🍒  attempts=9
ki            attempts=9
```

### 修复

`release()` 里把 `attempts` 归零——**主动放回不等于失败重试**。

### 验证

连续「认领→放回」5 次：

```

```

不再累加。既有 18 项中转站单测仍全部通过。

### 数据修复

把被误判的 4 条恢复成 pending、attempts 归零。
池：526 总数 / 521 待办 / 5 跳过（这 5 条是真的未核验）。

## 六十六、BUG 14：评论区里的作者昵称被当成了笔记标题（2026-11-02 07:25）

- 「共 N 条评论」行的 y
- 第一条评论时间锚点的 **y - 180**（评论正文在锚点上方约 160px 内，所以要再抬 180）

**2. 作者昵称本身不得作为标题**；评论标记词也排除。

**3. 无正文笔记不再整篇跳过**

标题读空说明这篇是纯图/纯视频，但**评论者是有价值的**。
以前这里直接跳过，等于把整篇线索扔掉。现在改成继续采评论，标题留空。

## 九十八、优化取号路径：单次 7.3s → 4.1s（2026-11-02 15:45）

主人确认：**小红书号只能点头像进主页才能拿到**，这条导航链没法省。
那就只省这一段里的等待。

### 原来每次取号在等什么

```
tap(头像)
pause(2.2)                       ← 等主页加载
settle()  = pause(0.6)+读树 ×2   ← 约 3.0 秒
press(BACK)
pause(1.5)
```

光等待约 **6.7 秒**，加上点击/返回约 7.3 秒/个。

### 改成自适应读取

```
tap(头像)
for delay in (1.3, 0.7, 0.7):
    pause(delay); 读号; 读到就 break
press(BACK); pause(1.0)
```

第一次就读到时只花 1.3 秒；读不到才补两次（**安全性不降级**，三次都失败才放弃）。

### 微基准实测（`data/bench_id.py`，同一篇笔记连取 4 个号）

```
[1] 🚗森垚yao是我吖～  95866412502   4.2s  读取1次  成功
[2] xx               490508569     4.0s  读取1次  成功
[3] xx               490508569     4.2s  读取1次  成功
[4] Ａｓｙ🌻           848774256     4.2s  读取1次  成功

成功率 4/4 = 100% | 平均 4.1s/个
```

**全部第一次读取就成功**，说明 1.3 秒足够主页加载；重试分支实际没触发。

### 收益

| 项 | 优化前 | 优化后 |
|---|---|---|
| 单次取号 | 约 7.3 秒 | **4.1 秒（−44%）** |
| 读号成功率 | 100% | **100%** |

按每轮约 10 个号算，单轮省 **约 32 秒（−10%）**。
这是今天最实打实的一次优化：**可靠性没动，纯省等待**。

## 一百零二、误点恢复：界面卡在评论区（2026-11-02 23:40）

### 现场

手机3 停在一个白底页面，上排「评论 / 赞和收藏」、底部「喜欢TA就给个评论支持一下～」。

**不是弹窗，是评论区被展开成全屏**，任务结束时没有收起，看起来就像卡死。

### 根因

采集收尾那段是这样写的：

```python
for _ in range(4):
    if any('EditText' in type(e) for e in tree()):
        break
    press('BACK')
```

它用「有没有 EditText」当作「回到搜索结果页」的判据。
但评论区展开时，输入框是 **TextView 占位符**（「喜欢TA就给个评论支持一下～」），
判据永远不成立 → 连按 4 次 BACK → 可能退出应用/停在奇怪页面，
而面板本身依然开着。

### 修复：借鉴抖音的三板斧

新增 `fishfleet/web/xiaohongshu_recover.py`：

| 手段 | 说明 |
|---|---|
| ① 标签兜底 | 见「我知道了/关闭/取消/暂不…」直接点掉（对应抖音 `_dismiss_popup`） |
| ② 状态识别 | Activity + 元素签名 → home/search/note/**sheet**/profile/chat/web |
| ③ 逐级回退 | 每次只按一次 BACK，重新判断状态，**不盲目连按** |
| ④ 兜底重启 | 逐级失败才重启应用回首页（对应抖音 recoverable 分支） |

接进采集流程的三处：

1. 每篇笔记采完 → `ensure_state('search')`，不再靠猜 BACK 次数；
2. 读评论抛异常 → 先把界面拉回结果页再继续下一条；
3. 多次点不进笔记 → 同样回退，避免在错页面打转。

### 第一次就修好了当前的卡死

```
当前状态: sheet | DetailFeedActivity
恢复: {'ok': True, 'steps': ['BACK（评论区（展开））', 'BACK（评论区（展开））'],
       'from': 'sheet', 'to': 'home'}
```

两次 BACK 就回到了首页。

### 一个被自己踩到的误判

最初判定「评论区展开」时，我把「底部有『说点什么…』」也算进去，
结果**普通笔记页一律被判成 sheet**（实测封面页就有这个占位符）。

改成只认「赞和收藏」页签后才正确。离线 9 个用例全过（`xiaohongshu_recover_selftest.py`）。

### 实测收尾

跑了一小轮采集（1 关键词 / 1 笔记 / 14 条评论 / 2 条线索），结束后：

```
收尾后状态: search | GlobalSearchActivity
```

界面干净地停在搜索结果页，不再残留面板。
