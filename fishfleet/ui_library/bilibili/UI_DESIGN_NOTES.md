# AI 助手「采集界面」设计思路

> 给子代理的参考文档。以 B站 截流面板为准，其他平台（抖音/小红书/TikTok）同理。
> 写的是**设计意图和踩过的坑**，不是代码说明书。

---

## 一、这东西到底在干什么

**一句话**：找到"在某类视频下留过言的人"，拿到他的账号 ID，然后给每个人准备一条个性化私信草稿，等人来点发送。

**三个不能妥协的底线**：

1. **只读采集** —— 不评论、不点赞、不关注、不分享
2. **只填草稿** —— 输入框里写好东西，**绝不点发送键**
3. **可追溯** —— 每条线索从哪来（哪个视频、哪条评论、哪个关键词）都要能查

**为什么强调"不发送"**：群控/自动化最大的风险是"手滑发出去"。所以设计上要让**发送路径根本不存在**，而不是靠"小心一点"。

## 二、界面的六个区块

从上往下：

```
┌─────────────────────────────────────────────────────┐
│ ① 关键词（一行一个）                                │
├──────────────────────┬──────────────────────────────┤
│ ② 参数              │                              │
│ 每个词看视频 [5]     │ 每视频读评论 [10]            │
│ 排序方式 [播放多▾]   │                              │
├──────────────────────┼──────────────────────────────┤
│ ③ 设备              │                              │
│ 采集用手机 [1][2][3] │ 回复用手机 [1][2][3]         │
├─────────────────────────────────────────────────────┤
│ ④ 文案                                              │
│ [— 选择常用语▾] [存为常用语] [删除]                 │
│ [文本域，支持 {昵称} {评论} {keyword}]              │
├─────────────────────────────────────────────────────┤
│ ⑤ 节流                                              │
│ 条数上限[50] 每条间隔(秒)[5] 每[10]条冷却[60]秒     │
├─────────────────────────────────────────────────────┤
│ ⑥ 操作                                              │
│ [开始采集] [开始回复] [停止]                        │
└─────────────────────────────────────────────────────┘
```

## 三、五个关键设计决策

### 决策 1：采集和回复**彻底分成两件事**

**不这么做的话**：一个按钮下去，采集和私信串在一起，出了问题分不清是谁的锅；也没法"用 3 台机器采、用 1 台机器发"。

**所以**：
- 两套设备选择器（`bl-collect-devices` / `bl-reply-devices`），各自独立
- 两个技能：`builtin:bilibili-lead`（采集）、`builtin:bilibili-dm`（回复）
- 两个按钮：开始采集 / 开始回复

**中转站是中转点**：采集往里写（pending），回复从里取（claimed → drafted）。

```
采集手机 ──写──▶ 中转站(pending) ──取──▶ 回复手机
                        │
                        └──▶ 人工审核 ──▶ 手动点发送
```

**好处**：
- 采集可以跑一整晚，回复第二天慢慢来
- 采集用性能好的机器，回复用登录了账号的机器
- 出问题能定位到具体是哪一段

### 决策 2：状态机只有四步，且**永远停在第 3 步**

```
pending（待处理）
   ↓ 领单
claimed（已认领，加了租约防重复）
   ↓ 填好草稿并验证
drafted（已填好，停在发送键前）  ←── 自动化到此为止
   ↓ 人工点发送
replied（已发送）
```

**关键**：自动化代码里**根本没有第 4 步**。

```python
# run_dm_task.py 里连这个函数都不调用
def send(dev, confirm=False):
    if not confirm:
        raise DMError('拒绝发送：必须显式传 confirm=True（这是人工确认位）')
```

**为什么加 `confirm=True`**：防止以后有人写代码时手滑 `dm_bili.send(dev)`。现在这样写会直接抛异常。

### 决策 3：审核标准要"看得见"

**不能只看数据库状态**——`drafted` 可能只是"函数没报错"，不代表字真的进去了。

**所以每个回复必须验证两件事**：

```python
# 1. 输入框里是不是我们想输的字（归一化去空白标点后逐字比对）
want, have = _norm(text), _norm(got)
if want != have and have[:8] != want[:8]:
    raise DMError('输入框内容和目标不符')

# 2. 发送按钮读不读得到（说明会话界面正常）
btn = next((r for r in raw(dev) if r['id'] == 'send_button'), None)
if btn is None:
    raise DMError('读不到发送按钮')
```

**结果记进 `extract_evidence`**：

```json
{"input_matched": true, "send_button": [1005, 1728], "session_title": "xxx"}
```

这样事后能查："这条到底验没验过"。

### 决策 4：设备选择**不复用全局选中**

B站截流面板有**自己的**两套 Set：

```js
const blCollect = new Set();   // 采集用
const blReply  = new Set();    // 回复用
```

**不复用 `state.selected`**（全局的），因为：
- 全局选中是给"发布/其他任务"用的
- 截流面板如果跟着全局走，切来切去会串

**UI 复用同一套样式**（`exec-phone-number`），但数据完全独立。

### 决策 5：节流要**两层**，不是一层

| 层 | 参数 | 作用 | 场景 |
|---|---|---|---|
| **每条间隔** | `interval_seconds` | 每条之间停一下 | 防止操作太快被判定为机器人 |
| **定期冷却** | `cooldown_every` / `cooldown_seconds` | 攒够 N 条停一大段 | 防止账号被风控 |

**为什么不能只有一层**：
- 只有间隔：50 条 × 5 秒 = 250 秒，看着像"匀速机器"
- 只有冷却：前 9 条连着发，太密

**两层叠加**才像真人：一条一条慢慢来，干一会儿歇一会儿。

**实现细节**：
- 最后一条**不等待**（否则跑完还干等）
- 停任务时**检查位置在每条之前**（不会卡在 sleep 里）

## 四、参数契约（给后端用）

```python
{
  "keywords": ["露营", "徒步"],          # 必填，最多 20 个
  "videos_per_keyword": 5,               # 每个词看几个视频
  "comments_per_video": 10,              # 每个视频读几条评论
  "sort_by": "播放多",                   # 默认排序/新发布/播放多/弹幕多
  "dm_template": "你好呀…{昵称}…{评论}…{keyword}…",

  "reply_limit": 50,                     # 本次最多回复几条
  "interval_seconds": 5,                 # 每条间隔
  "cooldown_every": 10,                  # 每 N 条
  "cooldown_seconds": 60,                # 冷却 M 秒
}
```

**注意**：模型里字段名要和前端传的一致。**Pydantic 会静默丢弃未知字段**——这是踩过的坑，前端传了 `sort_by` 但模型只有 `sort`，值直接没了，排查很久。

## 五、踩过的坑（重点，别重复）

### 坑 1：搜索框会被"搜索建议"抢

**现象**：输入「矿池」，搜索框变成「darkanddarker挖矿」；输入「挖矿木马」，变成「电脑中病毒cpu占用高」。

**原因**：B站 点搜索框时会自动填充建议词，`set_text` 写完立刻被覆盖。零延迟回车都拦不住。

**解法**：`set_text` 之后**立刻点「搜索」按钮**（`action_search`），不给建议词留时间。

**不要用**：`bilibili://search?keyword=` DeepLink——早期能用，后期 B站 记住状态后全部跳详情页。

### 坑 2：详情页有**多个** `id=title`

**现象**：`read_header` 读到的标题是「病毒」两个字（简介里的小标题），不是真标题。

**原因**：详情页同时有视频标题、简介内小标题、相关推荐标题。

**解法**：**标题优先用搜索卡片**（`card['title']`），详情页的只作兜底。

### 坑 3：Activity 栈会乱，BACK 回不到搜索页

**现象**：从详情页 BACK 一次，直接退到首页，搜索页被销毁，之后怎么 BACK 都回不去。

**解法**：每个视频采完**直接重搜**，不指望 BACK。代价是多花 10 秒，但状态永远干净。

### 坑 4：搜索页的搜索框是**只读**的

**现象**：连续搜索时，第二次写不进新词（还是上一次的）。

**原因**：结果页的搜索框是 `search_fake_text`（TextView，只读），要**点一下**才会展开成可编辑的 `search_src_text`。

**解法**：进搜索页分支里，先点一下搜索框再写。

### 坑 5：改去重键要重建索引，而且会被 skipped 行卡住

**现象**：`CREATE UNIQUE INDEX` 失败 —— `UNIQUE constraint failed`。

**原因**：判重后标成 `skipped` 的行还在表里，普通唯一索引会检查所有行。

**解法**：用**部分索引**：

```sql
CREATE UNIQUE INDEX idx_bilibili_key
ON leads_bilibili (commenter_uid, comment_author)
WHERE status != 'skipped'
```

### 坑 6：去重键要考虑"对业务意味着什么"

**原来的键**：`author + text + aid`
**问题**：同一个人在不同视频下评论 = 多条线索 = 私信发多次

**改成**：`commenter_uid + author`

**原则**：**去重键应该等于"业务上认为相同的粒度"**。对私信来说，一个人只需要联系一次。

## 六、给子代理的实现建议

### 顺序

1. **先做数据模型**（中转站表结构 + 状态机 + 去重键）
2. **再做采集**（搜索 → 视频 → 评论 → 取 UID）
3. **然后做回复**（领单 → 开会话 → 填草稿 → 验证）
4. **最后做界面**（设备选择、参数、节流）

### 每个功能都要问三个问题

1. **失败会怎样**？会不会把任务卡死？
2. **能不能验证**？怎么知道"真的成功了"而不是"没报错"？
3. **会不会越界**？有没有可能不小心执行了"发送/关注/点赞"？

### 硬规则

| 规则 | 原因 |
|---|---|
| 发送函数必须带 `confirm=True` | 防手滑 |
| 每条回复必须验"输入框内容 + 发送按钮" | 防假成功 |
| 设备选择各管各的 | 防串台 |
| 节流两层都要有 | 防风控 |
| 去重按业务粒度 | 防重复私信同一个人 |

### 别做的事

- **别用固定 `sleep` 等页面** —— 能轮询就轮询（实测能省 36% 时间）
- **别信"状态字段"** —— 要验证真实效果
- **别在采集里加发送能力** —— 哪怕"暂时不用"
- **别用 UI 文本做锚点** —— 用 `dumpsys` 里的 Intent 参数（`aid`/`uid` 这类数值）

---

## 七、一句话总结

> **把"机器能做的"和"必须人做的"用一条硬线分开：机器做到"东西都摆好了、验证过了"，人只负责最后那一下点击。**

界面上所有的分区、参数、验证、节流，都是为了这条线服务的。
